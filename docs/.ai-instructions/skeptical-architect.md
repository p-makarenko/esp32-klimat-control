# Метод Скептичного Архітектора

## Філософія
Агент моделює роботу команди експертів.
Мета: витриманий, протестований, еволюційний код.

## 7-Крокова Методологія

### Крок 1: Перша Ітерація - "Авторитетна Версія 1.0"
- Зрозуміти вимоги повністю
- Видати найочевидніше чисте рішення
- Стиль: впевнено, структуровано
- Короткі коментарі

**Результат:** Робоче рішення, готове до критики.

---

### Крок 2: Зміна Ролей - "Адвокат Диявола"
Автоматично перейти в режим критики.

**Знайти 3-4 слабкі місця:**
- Логічні дірки
- Edge cases (граничні випадки)
- Проблеми безпеки
- Performance bottlenecks

**Вимоги:**
- Конкретика, не загальні формулювання
- Контрприклади або сценарії збою
- Реальні ризики, не теоретичні

**Приклад критики:**
```
❌ Загально: "Цей код може мати проблеми"
✅ Конкретно: "Якщо WiFi відключиться під час запису в EEPROM,
   конфігурація буде пошкоджена. Немає перевірки CRC."
```

### Крок 3: "Системний Архітектор з Обмеженнями"
Переосмислити з творчим обмеженням.

**Альтернативні підходи:**
- Що якби пам'ять була обмежена?
- Що якби потрібна надійність 99.9%?
- Що якби це мало працювати без інтернету?

**Витягти інсайти:**
- Які архітектурні патерни застосовні?
- Які trade-offs робимо?
- Чи є простіше рішення?

### Крок 4: "Конкурент" (Конфлікт)
Сформулювати критику конкурентів.

**Що сказав би конкурент:**
- "Ваше рішення надто складне"

**Підготувати контраргументи:**

- Як покращити наше рішення?

### Крок 5: "Парі на $100" (Перевірка Рішучості)
Де найбільше сумніваєшся?

**Питання:**

- Який тест написати першим?
- Що викличе баг в продакшені?

**Результат:** Список точок підвищеної уваги.

---

### Крок 6: Синтез - "Версія 2.0"
Об'єднати інсайти з кроків 2-5.

**Дії:**
- Переосмислити, а не просто виправити
- Враховувати всі виявлені проблеми
- Додати захист від edge cases
- Розширені коментарі про рішення

**Результат:**
- Покращений код
- Список unit-тестів
- Документація рішень

**Приклад коментарів:**
```cpp
// Використовуємо CRC для перевірки цілісності конфігурації
// (критика з Кроку 2: ризик пошкодження при збої WiFi)
uint32_t crc = calculateCRC(configData);
prefs.putUInt("configCRC", crc);
```

### Крок 7: Фінальна Презентація
Пояснити як на технічному стендапі.

**Структура:**
1. **Рішення:** Що зробили і чому
2. **Альтернативи:** Що розглядали
3. **Компроміси:** Які trade-offs зробили
4. **Watch-outs:** На що звернути увагу в майбутньому

**Приклад:**
```
Рішення: Preferences замість EEPROM
Чому: NVS надійніший, wear leveling, більший розмір

Альтернативи розглядали:
- EEPROM: простіший, але обмежений життєвий цикл
- SPIFFS файли: гнучкіше, але повільніше

Компроміси:
- Трохи більше пам'яті
- Залежність від ESP-IDF

Watch-outs:
- Перевіряти CRC перед читанням
- Backup критичних налаштувань
- Тестувати з несправним flash
```

## Приклад Застосування

**Завдання:** Додати OTA оновлення

### Крок 1: Версія 1.0
```cpp
void setupOTA() {
    ArduinoOTA.begin();
}
```

### Крок 2: Критика
- Немає паролю → незахищено
- Немає callback → користувач не бачить прогрес
- Немає обробки помилок

### Крок 3: Альтернативи
- AsyncElegantOTA (готове рішення)
- Власна реалізація через HTTP
- Trade-off: простота vs контроль

### Крок 4: Конкурент
"ArduinoOTA застарілий, AsyncElegantOTA кращий"
Контраргумент: ArduinoOTA достатній, менше залежностей

### Крок 5: Парі
Найбільший ризик: OTA під час критичної операції
Тест: симулювати відключення під час оновлення

### Крок 6: Версія 2.0
```cpp
void setupOTA() {
    ArduinoOTA.setHostname("klimat");
    ArduinoOTA.setPassword(OTA_PASSWORD);
    
    ArduinoOTA.onStart([]() {
        // Зупинити критичні операції
        stopActuators();
        Serial.println("OTA Start");
    });
    
    ArduinoOTA.onProgress([](unsigned int progress, unsigned int total) {
        Serial.printf("Progress: %u%%\r", (progress * 100) / total);
    });
    
    ArduinoOTA.onError([](ota_error_t error) {
        Serial.printf("Error[%u]: ", error);
        // Детальна обробка помилок
    });
    
    ArduinoOTA.onEnd([]() {
        Serial.println("\nOTA Complete");
    });
    
    ArduinoOTA.begin();
}
```

### Крок 7: Презентація
Рішення: ArduinoOTA з паролем і callbacks
Альтернативи: AsyncElegantOTA (відхилили через складність)
Компроміси: трохи більше коду, але більше контролю
Watch-outs: тестувати з поганим WiFi, додати timeout
